Project settings, repeatable launches and safer financial records

This update helps Studio remember a project's build settings, lets Desk keep launching applications after earlier ones have closed, and tightens the shared financial records used by Trader and Bank. It also fixes a fault found when the shared directory walker visits an empty folder.

The source changes are in Framework, Studio and the Desktop/Desk module. Trader and Bank benefit through Framework; this package does not add a new broker connection, payment service or banking screen.

1. Before copying the files

Close the applications. Keep the previous Project Workflow update and its three-file Build Review correction in your checkout. This is the next changed-file update, not a replacement for the whole repository.

Review these repositories before merging. Run one line at a time and stop on an error:

Set-Location "C:\umicom\Umicom-Applications\framework"
git status

Repeat the status check in applications\studio, applications\desktop and the parent directory. Preserve any work you have not committed or backed up. Do not discard it to make the status look clean.

If the status says On branch main, you are already on the intended branch. If it says detached HEAD, compare the checked-out commit with main:

git rev-parse HEAD main

When the two hashes are identical and the working tree is clean, git switch main attaches the checkout without changing the source revision. When they differ, or there is unfinished work on another branch, stop and review that work before switching. Do not use a forced switch, reset or clean command.

2. Merge the source update

Extract the ZIP into a separate directory. Use Beyond Compare to merge the ZIP's umicom-applications folder into:

C:\umicom\Umicom-Applications

On Linux, the examples use:

$HOME/umicom/Umicom-Applications

Keep the spelling and case of your actual Linux checkout. Do not create a second nested umicom-applications folder.

Do not mirror-delete files that are absent from this ZIP. There are no folder moves and no git mv commands. The package includes only new or changed files. The earlier build CLI fallback, generic unset Run default, Output counters and all 64 existing lessons are preserved.

3. Configure and build everything on Windows

Run each command separately. If configuration or building fails, stop before installing or publishing and keep the error output.

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

Configure:

& "C:\msys64\ucrt64\bin\cmake.exe" --preset windows-ucrt64-all-debug -DBUILD_TESTING=ON -DUMICOM_BUILD_NATIVE_TOOL=ON -DUMICOM_BUILD_LEARNING_EXAMPLES=ON -DUMICOM_LEARNING_BUILD_GUI=ON

Build:

& "C:\msys64\ucrt64\bin\cmake.exe" --build --preset windows-ucrt64-all-debug --parallel 2 -- -k 0

The final -k 0 asks Ninja to continue independent build work so that the log can show more than one error. A failed build is still a failed build; continuing independent jobs does not make it suitable for installation.

4. Test the Windows build

Run the three focused groups separately. An absent required group should report an error rather than be hidden by unrelated passing tests.

& "C:\msys64\ucrt64\bin\ctest.exe" --preset windows-ucrt64-all-debug --parallel 1 --no-tests=error --output-on-failure -R '^framework\.operational_state\.'

& "C:\msys64\ucrt64\bin\ctest.exe" --preset windows-ucrt64-all-debug --parallel 1 --no-tests=error --output-on-failure -R '^studio\.(project_settings\.|project_workflow$)'

& "C:\msys64\ucrt64\bin\ctest.exe" --preset windows-ucrt64-all-debug --parallel 1 --no-tests=error --output-on-failure -R '^desktop\.launch_lifecycle$'

Then run the complete suite:

& "C:\msys64\ucrt64\bin\ctest.exe" --preset windows-ucrt64-all-debug --parallel 2 --no-tests=error --output-on-failure

Read the final summary. Failed, disabled, skipped and Not Run tests are different results. In particular, a skipped SQLite test is not proof that settings survive a restart. Keep the logs with your build evidence. Linux test results shipped with the batch do not replace these Windows checks.

5. Check Studio by using a Notes project

Start the build-tree Studio:

& ".\build\windows-ucrt64-all-debug\bin\umicom-studio-ide.exe"

Use a disposable Umicom Notes project, not your main Applications source tree. Create it through File → New Project, or open a small existing project that you own. Under Build → Project Settings, choose its build directory, compiler/preset and actual executable. An imported project deliberately starts without a guessed Run target.

Save the settings and note their values. Close Studio normally, reopen it, and open the same project folder. The saved fields should return, including an explicitly blank Run program. The settings are per-user and per-platform. They are not copied to another computer by Git.

Restored settings must not silently restore trust. Review and explicitly trust only your own project before allowing its build scripts or executable to run. Configure, build and run it. Edit a source file, save it and build again. Introduce a small compile error in this disposable project: Run should stop rather than launch the older executable. Remove the error and rebuild.

For a settings-conflict check, open the same project in two Studio instances. Save a different setting in the first. Saving the older settings in the second should report a conflict. Reopen that workspace to load the saved revision before editing it again; the older instance must not overwrite silently.

A corrupt stored profile should be reported and preserved, not replaced automatically with default values. Do not delete your workspace database as a routine repair; it may also contain your saved layouts.

The service-level reopen, conflict and failure paths were executed in the supplied tests. These mouse-and-keyboard checks of the GTK forms still need to be completed on your native machine.

6. Check Desk, Trader and Bank

Close Studio, then start Desk:

& ".\build\windows-ucrt64-all-debug\bin\umicom-desk.exe"

Launch a harmless application, close it, and launch it again. The current runtime state should follow the new process. An old process's delayed exit must not stop the new instance. The automated test repeats 72 actual launches of an inert test child, including the former failure point at launch 65; it does not launch banking or trading products 72 times.

Open Trader and Bank separately to check ordinary startup and shutdown:

& ".\build\windows-ucrt64-all-debug\bin\umicom-trader.exe"

& ".\build\windows-ucrt64-all-debug\bin\umicom-bank.exe"

Use synthetic accounts and simulation/paper data only. The new tests check shared identifiers, account balances, holds, transactions and non-finite Trader drafts. They do not establish a complete Bank service, a live broker connection or correct live market-order valuation. The pretrade reference-price fallback of 1.0 is still outstanding.

7. Install into a separate Windows directory

Close the applications first. Choose a new installation directory; preserve any earlier one.

Set-Location "C:\umicom\Umicom-Applications"
$Stage = "C:\umicom\installed\operational-state-validation"
Test-Path -LiteralPath $Stage

If that last command prints True, change $Stage to a new directory before continuing. Do not install over the earlier copy.

& "C:\msys64\ucrt64\bin\cmake.exe" --install ".\build\windows-ucrt64-all-debug" --config Debug --prefix $Stage

After installation succeeds, check an installed command:

$env:Path = "$Stage\bin;C:\msys64\ucrt64\bin;$env:Path"
& "$Stage\bin\umicom-source-contracts.exe" --help

Start the installed Studio from outside the source checkout:

Set-Location $env:TEMP
& "$Stage\bin\umicom-studio-ide.exe"

Repeat the project-settings/reopen checks, then try installed Desk, Trader and Bank using their full paths under $Stage\bin. This is a development installation using your MSYS2 runtime. It is not yet evidence of a self-contained end-user installer.

8. Make a Windows deployment ZIP

This step is required before distributing an archive, but not for every source-only commit. Use a new package-output directory.

Set-Location "C:\umicom\Umicom-Applications"
& "C:\msys64\ucrt64\bin\cpack.exe" --config ".\build\windows-ucrt64-all-debug\CPackConfig.cmake" -G ZIP -C Debug -D CPACK_ARCHIVE_COMPONENT_INSTALL=OFF -B "C:\umicom\packages\operational-state-validation"

After packaging succeeds, inspect the ZIP and record its checksum:

Get-ChildItem "C:\umicom\packages\operational-state-validation\*.zip" | Get-FileHash -Algorithm SHA256

Extract the ZIP into a new deployment directory. Start its executables, not the build-tree copies, and repeat the native checks. A clean-machine test is still needed before calling the archive self-contained. Do not distribute user configuration databases, credentials, live account information or your working project directories.

9. Linux build, test, install and package

The native Linux preset requires the project's GTK4 development dependencies and compiler. Do not lower its GTK requirement or invent a substitute adapter to make configuration pass.

cd "$HOME/umicom/Umicom-Applications"
cmake --preset linux-all-gtk4-debug -DBUILD_TESTING=ON -DUMICOM_BUILD_NATIVE_TOOL=ON -DUMICOM_BUILD_LEARNING_EXAMPLES=ON -DUMICOM_LEARNING_BUILD_GUI=ON
cmake --build --preset linux-all-gtk4-debug --parallel 2 -- -k 0

Run each focused group and then the complete suite, stopping at a failure:

ctest --preset linux-all-gtk4-debug --parallel 1 --no-tests=error --output-on-failure -R '^framework\.operational_state\.'
ctest --preset linux-all-gtk4-debug --parallel 1 --no-tests=error --output-on-failure -R '^studio\.(project_settings\.|project_workflow$)'
ctest --preset linux-all-gtk4-debug --parallel 1 --no-tests=error --output-on-failure -R '^desktop\.launch_lifecycle$'
ctest --preset linux-all-gtk4-debug --parallel 2 --no-tests=error --output-on-failure

The headless preset used for this delivery is linux-gcc-all-headless-debug. It builds and tests the service paths without GTK. Use that preset when checking the same headless configuration; a successful headless run is not a graphical acceptance test.

After a native build, start each application separately and close it before starting the next:

./build/linux-all-gtk4-debug/bin/umicom-studio-ide
./build/linux-all-gtk4-debug/bin/umicom-desk
./build/linux-all-gtk4-debug/bin/umicom-trader
./build/linux-all-gtk4-debug/bin/umicom-bank

Install into a new development prefix:

stage="$HOME/umicom/installed/operational-state-validation"
test -e "$stage" && printf '%s\n' 'Directory already exists: choose a different stage path.'

Continue only after you have chosen an absent path. Then:

cmake --install build/linux-all-gtk4-debug --config Debug --prefix "$stage"
"$stage/bin/umicom-source-contracts" --help
cd /tmp
"$stage/bin/umicom-studio-ide"

Repeat the native checks in the installed copy. Package from the source root:

cd "$HOME/umicom/Umicom-Applications"
cpack --config build/linux-all-gtk4-debug/CPackConfig.cmake -G TGZ -C Debug -D CPACK_ARCHIVE_COMPONENT_INSTALL=OFF -B "$HOME/umicom/packages/operational-state-validation"
sha256sum "$HOME/umicom/packages/operational-state-validation/"*.tar.gz

Extract into a new directory and test there. System GTK libraries remain dependencies unless the packaging work explicitly bundles and qualifies them.

11. Lock and publish the parent last

Only continue when every changed child repository has been committed and pushed. If another submodule still contains intended edits, finish publishing it first.

Windows

Set-Location "C:\umicom\Umicom-Applications"
git status
git switch main
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
& ".\build\windows-ucrt64-all-debug\bin\umicom.exe" repo lock .

After the lock succeeds:

git add -A
git diff --cached --check
git diff --cached --submodule=log
git commit -m "chore(applications): integrate operational state fixes and record child revisions"
git push --recurse-submodules=check origin main
git status

Linux

cd "$HOME/umicom/Umicom-Applications"
git status
git switch main
./build/linux-all-gtk4-debug/bin/umicom repo lock .

After the lock succeeds:

git add -A
git diff --cached --check
git diff --cached --submodule=log
git commit -m "chore(applications): integrate operational state fixes and record child revisions"
git push --recurse-submodules=check origin main
git status

For a deliberately headless qualification, use the native umicom command from build/linux-gcc-all-headless-debug/bin instead. Do not skip the lock because a different build directory was used.

The parent push checks that changed submodule commits are available through a submodule remote. It is not a substitute for pushing the intended child's main branch first. No commits or pushes were made by the preparation of this package.

12. Confirm and update another machine

From the parent repository:

git status
git submodule foreach --recursive 'git status --short --branch'

The parent should have no pending changes. Inspect each child status as well. A clean working tree is not, by itself, proof that unpushed commits have reached GitHub; keep the successful push output.

On another machine, start with a clean checkout with no uncommitted child work. Then run from the parent:

git switch main
git pull --ff-only origin main
git submodule sync --recursive
git submodule update --init --recursive

That last command checks out the exact child revisions recorded by the parent. Detached child checkouts are normal for reproducing that snapshot. Do not switch every child to a newer branch tip just to make the status say main. Attach a child before editing it, using section 1's comparison.

Saved Studio settings are not part of the source checkout. On the second machine, review its own compiler, executable paths and workspace trust. This package does not synchronise user settings or trust through Git.

13. What remains before the five products are complete

Priority Next work How to prove it
Framework and Studio Compile and exercise the native Windows/Linux GTK paths, including save/reopen, workspace transitions, shutdown and output. Native build logs plus real GUI acceptance checks, not catalogue or source-string tests alone.
Studio Portable project configuration, multiple targets/projects, interactive Run input, LSP/debugger/designer qualification. Repeatable end-to-end use of real tools and saved projects. This update adds local profile persistence, not all of those features.
Desk Native launch/taskbar updates, application activation/focus, failed launches and shutdown with several products running. Tests and observed native behaviour; the current repeated-launch test uses an inert child.
Trader Authoritative market references, stale-data and instrument valuation rules, paper lifecycle/reconciliation and broker-specific validation. Independent valuation and paper execution evidence. The 1.0 market-order fallback is still a blocker for live valuation.
Bank Bind screens to approved account/ledger/payment services with permissions, atomic financial effects, reconciliation and recovery. Synthetic end-to-end account and payment workflows through the Data Server. Record validation alone is not a banking platform.
