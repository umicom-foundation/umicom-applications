Umicom Programming Workshop — Batch Guide

Framework-owned lessons for Studio and Education
Sammy Hegab · Umicom Foundation · 16 September 2026

Start here

This batch adds the complete Git beginners guide and 32 executable programming lessons to the existing Framework catalogue. There are now 53 catalogue entries: 20 preserved lessons + 33 additions. The Git lesson contains commands and personal repository exercises; the other 32 additions contain complete C programmes, with native Assembly comparisons in two of them.

Run one command at a time. Read its output. Stop at the first error. These instructions contain no all-repository publishing script and no capitalised confirmation prompts. A commit is not evidence that the code was built or tested.

This is a changed-file source delivery, not a prebuilt release or a promise that every programming concept is covered. Windows and graphical checks below are qualification steps to perform on your machine.

2. Before merging: check the two repositories

Use the commands for your operating system. Do this before merging, while your own existing work is preserved.

Windows

Set-Location "C:\umicom\Umicom-Applications\framework"
git status

If this says On branch main, continue. If it is clean but detached, compare:

git rev-parse HEAD main

Only when both hashes are identical, attach to the same revision:

git switch main
git status

Repeat the check for Education:

Set-Location "C:\umicom\Umicom-Applications\applications\education"
git status

If clean and detached, use the same git rev-parse HEAD main comparison before git switch main. If the hashes differ, main is missing, or there is uncommitted work on another branch/detached HEAD, stop and preserve it. Do not use a forced switch or reset. See the Git lesson's branch section for the explanation.

Linux

cd "$HOME/umicom/Umicom-Applications/framework"
git status

For a clean detached checkout, compare git rev-parse HEAD main. When identical:

git switch main
git status
cd "$HOME/umicom/Umicom-Applications/applications/education"
git status

Apply the same branch condition to Education. Linux paths are case-sensitive; these examples use the exact checkout name Umicom-Applications.

4. Build and test the lessons first

The standalone programming project needs GCC/Clang with the required C mode, CMake and Ninja. It does not need GTK or the full application build. Keep its build directory separate from the main application build.

Windows — 32 new executable lessons

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
& "C:\msys64\ucrt64\bin\cmake.exe" -S ".\framework\examples\learning\programming" -B ".\build\learning-programming" -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_C_COMPILER="C:/msys64/ucrt64/bin/gcc.exe" -DCMAKE_MAKE_PROGRAM="C:/msys64/ucrt64/bin/ninja.exe" -DUMICOM_LEARNING_BUILD_ASSEMBLY=ON
& "C:\msys64\ucrt64\bin\cmake.exe" --build ".\build\learning-programming" --parallel 2
& "C:\msys64\ucrt64\bin\ctest.exe" --test-dir ".\build\learning-programming" --no-tests=error --output-on-failure

Expect 32 tests. Read the summary; do not proceed on failures or missing tests.

Windows — catalogue and resource integrity

& "C:\msys64\ucrt64\bin\cmake.exe" -S ".\framework\tests\release_qualification" -B ".\build\learning-qualification" -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_C_COMPILER="C:/msys64/ucrt64/bin/gcc.exe" -DCMAKE_MAKE_PROGRAM="C:/msys64/ucrt64/bin/ninja.exe"
& "C:\msys64\ucrt64\bin\cmake.exe" --build ".\build\learning-qualification" --parallel 2
& "C:\msys64\ucrt64\bin\ctest.exe" --test-dir ".\build\learning-qualification" --no-tests=error --output-on-failure

Expect 6 tests, including the existing naming checks and the extended catalogue/resource checks. This is not the full application suite.

Linux — equivalent focused checks

cd "$HOME/umicom/Umicom-Applications"
cmake -S framework/examples/learning/programming -B build/learning-programming -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_C_COMPILER=gcc -DUMICOM_LEARNING_BUILD_ASSEMBLY=ON
cmake --build build/learning-programming --parallel 2
ctest --test-dir build/learning-programming --no-tests=error --output-on-failure
cmake -S framework/tests/release_qualification -B build/learning-qualification -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_C_COMPILER=gcc
cmake --build build/learning-qualification --parallel 2
ctest --test-dir build/learning-qualification --no-tests=error --output-on-failure

Native Assembly is supplied for x86-64 Windows/ELF and RISC-V LP64 ELF. On another architecture use -DUMICOM_LEARNING_BUILD_ASSEMBLY=OFF; the two comparison programmes explicitly identify their C-only mode. A C-only pass is not an Assembly pass. This delivery executed Linux x86-64 Assembly; Windows and RISC-V object assembly was checked but those objects were not executed.

Run one example

Windows:

& ".\build\learning-programming\bin\umicom-learning-bounded-strings.exe"

Linux:

./build/learning-programming/bin/umicom-learning-bounded-strings

The example rejects malformed and oversized strings, accepts an exact fit, and prints PASS: bounded_strings. Each lesson names its own file, target, executable and expected checks. A failed process result matters even if some output looks correct.

Do not install or publish a release with failed, missing or required-but-skipped checks. An unrelated existing suite failure is still a qualification item, not something to hide by deleting its test.

9. Commit and push the changed repositories

Review changes and qualification evidence first. git add -A stages all changes in the current repository, including deletions. Exclude secrets, temporary programmes, unrelated changes and build output. These steps intentionally name only the three changed repositories.

The pre-merge checks in section 2 should already have put the two child repositories on main. If the status below unexpectedly reports another branch or detached HEAD with changes, stop before switching and preserve the work. Do not run a forced switch.

Framework — first

Set-Location "C:\umicom\Umicom-Applications\framework"
git status
git switch main
git status
git add -A
git diff --cached --check
git commit -m "feat(learning): expand shared programming curriculum and runnable labs"
git push origin main

No output from git diff --cached --check is normal. If it reports a problem, stop before the commit. If Git says nothing to commit, working tree clean, skip another commit and proceed to the push. Everything up-to-date is a normal push result for an unchanged branch. Other errors require attention.

Education — second

Set-Location "C:\umicom\Umicom-Applications\applications\education"
git status
git switch main
git status
git add -A
git diff --cached --check
git commit -m "feat(education): expose the shared Framework lesson catalogue"
git push origin main

Parent Applications — last

After both child pushes succeed:

Set-Location "C:\umicom\Umicom-Applications"
git status
git switch main
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
& ".\build\windows-ucrt64-all-debug\bin\umicom.exe" repo lock .

Only after the native lock succeeds:

git add -A
git diff --cached --check
git diff --cached --submodule=log
git commit -m "docs(applications): integrate programming workshop and record child revisions"
git push --recurse-submodules=check origin main
git status

The expected final parent state is clean and up to date. A dirty child is not repaired by committing the parent. The parent stores child revision IDs, not the files staged inside a child.

10. Clone or update a different machine

New Windows checkout

From an existing writable C:\umicom directory, with GitHub access configured:

Set-Location "C:\umicom"
git clone --recurse-submodules https://github.com/umicom-foundation/umicom-applications.git Umicom-Applications
Set-Location "C:\umicom\Umicom-Applications"
git status

Do not clone over an existing checkout. Use the update instructions instead.

New Linux checkout

mkdir -p "$HOME/umicom"
cd "$HOME/umicom"
git clone --recurse-submodules https://github.com/umicom-foundation/umicom-applications.git Umicom-Applications
cd Umicom-Applications
git status

Update an existing receiving checkout

First review and preserve local changes in the parent and its children. This inspection runs no writes:

git status
git submodule foreach --recursive 'git status --short --branch'

Only with a clean receiving checkout, run from the parent:

git switch main
git pull --ff-only origin main
git submodule sync --recursive
git submodule update --init --recursive
git status

These Git commands work in PowerShell and a Linux terminal. The update restores the recorded child commits; it does not ask for each child's newest independent branch tip. Detached submodules are normal for this receiving/build-only state. Do not add --remote merely to remove a detached-HEAD message. For development, follow the individual safe branch checks before editing.

Build again on the receiving machine. Do not copy Windows build output into a Linux build directory.

11. Coverage and remaining work

The executable lessons cover representation, basic CPU execution, values, control flow, contracts, arrays, strings, parsing, structures, enumerations, ownership, allocation, arithmetic, floating point, files, modules, callbacks, controllers, state machines, bounded queues, search/sort, testing, naming, macros, binary encoding, recursion, atomic API basics and two Assembly comparisons.

Further tracks remain: fuller operating-system architecture and processes, memory mapping, real thread synchronisation and race testing, network programming, Unicode, richer data structures, debugger sessions, more CPU architectures, deeper Framework API projects, and application-integrated exercise execution with permissions, cancellation and durable evidence. They are not silently marked completed by this delivery.
