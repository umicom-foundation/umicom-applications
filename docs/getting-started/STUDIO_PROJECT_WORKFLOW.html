Studio project workflow — build, test, install and publish

Start by building the updated Studio. Then create a fresh Umicom Notes project and follow it from the first edit to an installed executable. Run one command at a time, and stop when a command fails.

Preparation status: the real Linux headless workflow is tested. The new GTK code is supplied for native qualification; Windows and GTK execution remain to be checked.

1. Check your checkout before merging

Close Studio before replacing its source. This update changes Framework and Studio. The other application sources stay as they are.

In PowerShell, check the three repositories:

Set-Location "C:\umicom\Umicom-Applications"
git status
git -C framework status
git -C applications/studio status

When a repository already says On branch main, leave it there. Review and preserve any unrelated changes before merging the files.

A clean detached submodule is not necessarily broken: it may be at the exact revision recorded by the parent. Before moving it to main, run git rev-parse HEAD main inside that submodule. If both hashes match, git switch main attaches the same source to the branch. If they differ, stop and preserve or reconcile that work before switching. Do not use switch --discard-changes, reset --hard or force-push.

The archive was prepared against your uploaded source, not a newly pulled checkout. The changed-file manifest records the original and updated SHA-256 for each replacement. A different original hash means that file needs a careful comparison rather than a blind overwrite.

2. Merge the source update

Extract the update into a separate folder. Open Beyond Compare and compare the archive's umicom-applications directory with:

C:\umicom\Umicom-Applications

Copy the new and changed files into their matching locations. Keep the other files in your checkout. Do not use mirror deletion: this ZIP deliberately omits unchanged source. There are no folder moves, git mv steps or replacement .git files.

On Linux, compare the same archive directory with $HOME/umicom/Umicom-Applications. The relative paths are identical. Keep any local modifications that are not part of this update.

The new course starts at framework/docs/learning/application-development.html. You can read it in a browser while building the examples.

3. Configure and build everything on Windows

Run each command separately. Read its result before continuing. A configuration or build error means stop; do not install the previous executable and assume it contains this update.

Set the working directory and make the UCRT64 tools available:

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

Configure the complete application build, including the native Umicom tool and the learning examples:

& "C:\msys64\ucrt64\bin\cmake.exe" --preset windows-ucrt64-all-debug -DUMICOM_BUILD_NATIVE_TOOL=ON -DUMICOM_BUILD_LEARNING_EXAMPLES=ON -DUMICOM_LEARNING_BUILD_GUI=ON

Build it:

& "C:\msys64\ucrt64\bin\cmake.exe" --build --preset windows-ucrt64-all-debug --parallel 2 -- -k 0

The two-job limit keeps resource use modest. Ninja's -k 0 continues independent work so you can see more than the first build failure. It does not turn failures into successes. CMake presets define the shared configuration; see the official CMake reference at the end.

4. Run the focused checks, then the complete suite

First run the project workflow, lessons, document boundaries and source-contract checks:

& "C:\msys64\ucrt64\bin\ctest.exe" --preset windows-ucrt64-all-debug --parallel 2 --no-tests=error --output-on-failure -R '^(studio\.project_workflow$|framework\.(ide_workflow\.|learning\.projects\.|source_contracts\.|teacher\.))'

Then run every test registered by the Windows build:

& "C:\msys64\ucrt64\bin\ctest.exe" --preset windows-ucrt64-all-debug --parallel 2 --no-tests=error --output-on-failure

--no-tests=error prevents an empty selection from looking like a successful test run. Read skipped tests as well as failures. The new GTK form test returns a skip when it cannot connect to a display; a skipped form test is not evidence that the interface works.

studio.project_workflow creates its own small project under the build tree. It actually edits, saves, configures, builds, runs, tests and installs that project, then introduces a compiler error and checks that Run stops. It also repeats test discovery to exercise suite replacement and shutdown. It never uses a live bank account, broker or payment connection.

5. Start the rebuilt Studio

Start the build-tree executable:

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
& ".\build\windows-ucrt64-all-debug\bin\umicom-studio-ide.exe"

Use a disposable project for the first check. Do not open a production payment workspace or use live trading as a smoke test.

The following walkthrough is the native acceptance check still required for this update. The Linux service tests have passed, but the new GTK source has not been compiled or clicked through in the preparation environment.

6. Create a new Umicom Notes project

Choose File → New Project. Use these values:

Field Value
Template C23 Console Application
Application name Umicom Notes
Application identifier org.umicom.notes
Repository name umicom-notes
CMake target umicom_notes
New project folder C:\umicom\projects\UmicomNotes

Choose a destination that does not already exist. The form creates the folder for you. It does not download a Framework checkout, initialise Git, build the project or grant trust.

Select Create Project. Expect the workspace to change to the new project and src/main.c to open. The initial files include CMakeLists.txt, CMakePresets.json, source, a README, a simple test and an ignore file.

Open Build → Project Settings. Check the source path, preset, executable and install path. Review the generated files, then select the checkbox confirming that you trust this project's code and build scripts. Apply the settings.

The C23 console starter is sufficient for the first activity-report lesson. The later banking and Notes model examples call Framework APIs and are built as learning targets in your Applications checkout; do not copy their includes into an unlinked plain-C project and expect the linker to find Framework automatically.

7. Edit, save, build and run

Open the first application lesson, Write an activity report for Umicom Notes. Type its example into the generated src/main.c. Save the file.

Choose Build. The background workflow configures and compiles the project. Studio should continue repainting while the compiler runs. Open the Build panel for phase progress and Output for the latest completed phase's text.

Choose Run. It configures and builds before launching the program, so a failed compile must not launch an older executable. The report should show three saved notes and one pending note. Change the saved count to four, save, build and run again. Check the changed output.

Choose Test, then Install. Test and Install configure and build all targets before the final phase. The generated starter's test is only a smoke test: it confirms that the test mechanism is connected, not that a banking or note-saving rule is correct. The supplied Notes model has separate behavioural tests.

For this project, the installed program is under install/windows-ucrt64-debug/bin/umicom_notes.exe. Use the profile's install folder to confirm the exact location.

Output currently displays the latest completed phase, not a continuously streaming terminal. Older phase records remain in build history. Interactive standard input is not implemented by this new build route.

8. Check errors and unsaved work

Add this line to src/main.c, save and choose Run:

#error Umicom_expected_compile_failure

The compiler must fail, Output must show the error, and the program must not start. Remove the line, save and run again.

Create another source document with File → New File. Type a note into it but do not choose a path yet. Request a build. Studio should ask you to save unnamed documents rather than silently ignore them. Use Save As, then try again.

With two named source files open, edit both and request a build. Both drafts must reach disk. Saving another tab should not move the active tab or reset its cursor unnecessarily. An untouched built-in welcome document should not block Save All; editing that document makes it a draft that needs Save As.

In a disposable file only, change the same file outside Studio after editing it inside Studio. Saving must report the conflict rather than overwrite the external change. Close a modified document and check the discard warning. Cancel a build and confirm that a later operation can start after completion and result collection.

These checks should be repeated through the main menu, toolbar and Search Everywhere. The canonical build commands in Search Everywhere now use the same background route, but this must still be verified in a native GTK run.

9. Open an existing project

Use File → Open Folder for an existing CMake project. Opening the folder changes the build profile's source root; it must no longer point to the previous project. The folder initially remains untrusted.

Open Build → Project Settings and review these fields:

Field How to use it
Project folder Read-only identity of the current workspace.
CMake preset A real configure preset in that project's CMakePresets.json, or blank for explicit fields.
Build folder The directory produced by that preset, or the explicit build directory when no preset is used.
Generator and compiler Used for an explicit configuration. A populated preset controls its own configuration.
Build target Blank builds all targets. Test and Install build all targets before continuing.
Program to run Set it explicitly for an imported project; it starts blank rather than defaulting to Studio.
Program argument One argument, not a shell command line. No shell expansion is performed.
Install folder A separate development prefix you own.

For an explicit Ninja build, a typical Windows executable path is build/umicom-development/bin/your_target.exe; on Linux omit .exe. The project may use another output layout, so check its CMake rules.

With the Operational State update, Studio saves reviewed project settings through its existing per-user Data Server and restores them when the same workspace is opened again. The native host uses its workspace SQLite storage; memory-only hosts retain settings only while that Data Server exists. Workspace trust is still an explicit choice and is not restored from a build profile. Settings are local to the user and platform; cloning the source on another machine does not copy them. See the update guide for the reopen and conflict checks.

10. Use the lessons and the Notes window

In Studio, choose Help → AI Teacher to open Guided Learning. Framework's catalogue supplies the new lesson cards to Studio and the Education catalogue frontend. Select a lesson by its title. The browser entry point is:

framework/docs/learning/application-development.html

To run the supplied Notes window after the graphical build:

& ".\build\windows-ucrt64-all-debug\bin\umicom-learning-notes-window.exe"

The window uses Framework component specifications for its window, boxes, labels, split panels, entry, buttons, text view and scrolling. Menus and a button call the same Framework-backed Notes commands. Choose a new filename in your own directory, save a note, edit it, use Undo and test the close warning. Deliberately deleting all text from a saved note is still an unsaved change.

The learning targets share one Notes model. They do not replace the Framework document store with an application-local file system. The terminal example and the window both use the existing document coordinator and command registry.

The course links the new application exercises to the existing lessons on C, memory, binary, Assembly, algorithms, architecture, testing and Git. Later work should extend these same applications with Data Server persistence, richer widget models, accessibility, networking and debugging.

11. Install into a fresh Windows development directory

Close the applications after the build-tree checks. Choose an unused destination:

Set-Location "C:\umicom\Umicom-Applications"
$Stage = "C:\umicom\installed\studio-project-workflow"
Test-Path -LiteralPath $Stage

The result must be False. If it is True, keep that installation and choose another directory. Then install:

& "C:\msys64\ucrt64\bin\cmake.exe" --install ".\build\windows-ucrt64-all-debug" --config Debug --prefix $Stage

Check the installed copies from outside the source tree:

$env:Path = "$Stage\bin;C:\msys64\ucrt64\bin;$env:Path"
Set-Location $env:TEMP
& "$Stage\bin\umicom-source-contracts.exe" --help
& "$Stage\bin\umicom-learning-account-totals.exe"
& "$Stage\bin\umicom-studio-ide.exe"

Repeat New Project, editing, building and lesson opening in the installed Studio. The learning HTML is installed under share/umicom-framework/docs/learning.

This is a development installation using the existing MSYS2 runtime. It is not proof of a self-contained installer for a computer without that runtime. Keep the old working installation until the new one passes the checks.

12. Create and check a deployment archive

After installation and smoke testing succeed:

Set-Location "C:\umicom\Umicom-Applications"
& "C:\msys64\ucrt64\bin\cpack.exe" --config ".\build\windows-ucrt64-all-debug\CPackConfig.cmake" -G ZIP -C Debug -B "C:\umicom\packages\studio-project-workflow"

CPack prints the archive filename. Extract that archive into a new directory and repeat the installed checks from the extracted copy. A clean-machine test is required before describing it as an end-user package. Do not package or distribute credentials, local banking data or live broker settings.

13. Build and test on Linux

For terminal and service work, use the all-module GCC headless preset:

cd "$HOME/umicom/Umicom-Applications"
cmake --preset linux-gcc-all-headless-debug -DUMICOM_BUILD_NATIVE_TOOL=ON -DUMICOM_BUILD_LEARNING_EXAMPLES=ON
cmake --build --preset linux-gcc-all-headless-debug --parallel 2
ctest --preset linux-gcc-all-headless-debug --parallel 2 --no-tests=error --output-on-failure

For Studio's actual graphical interface, use a desktop environment with the project's GTK4 development dependencies installed:

cd "$HOME/umicom/Umicom-Applications"
cmake --preset linux-all-gtk4-debug -DUMICOM_BUILD_NATIVE_TOOL=ON -DUMICOM_BUILD_LEARNING_EXAMPLES=ON -DUMICOM_LEARNING_BUILD_GUI=ON
cmake --build --preset linux-all-gtk4-debug --parallel 2
ctest --preset linux-all-gtk4-debug --parallel 2 --no-tests=error --output-on-failure
./build/linux-all-gtk4-debug/bin/umicom-studio-ide
./build/linux-all-gtk4-debug/bin/umicom-learning-notes-window

Do not substitute a headless test result for the graphical checks in sections 6–10. For a generated Linux console project, the preset is linux-debug, the program has no .exe suffix and its install prefix is install/linux-debug.

Install a qualified graphical build into a fresh development prefix, then run outside the checkout:

cd "$HOME/umicom/Umicom-Applications"
cmake --install build/linux-all-gtk4-debug --config Debug --prefix "$HOME/umicom/installed/studio-project-workflow"
cd /tmp
"$HOME/umicom/installed/studio-project-workflow/bin/umicom-studio-ide"

Package it with the existing CPack rules:

cd "$HOME/umicom/Umicom-Applications"
cpack --config build/linux-all-gtk4-debug/CPackConfig.cmake -G TGZ -C Debug -B "$HOME/umicom/packages/studio-project-workflow"

14. Commit and push Framework, then Studio

Review the files before staging. git add -A includes every intended addition, modification and deletion in the current repository, not just this batch. A commit saves source history; it does not certify a native release. Complete the native checks before marking the release qualified.

These commands assume the safe branch check in section 1 is complete. Stop on an error. “Nothing to commit, working tree clean” is normal when there are no new changes; continue to the push. Do not force a rejected push.

15. Update and publish the parent last

Continue only after the child pushes succeed. Run the native repository lock command from the Applications root. If the tool is missing or the command fails, stop; do not invent a lock file or publish an old one.

Windows

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
git status
git switch main
& ".\build\windows-ucrt64-all-debug\bin\umicom.exe" repo lock .

After the lock succeeds:

git add -A
git diff --cached --check
git diff --cached --submodule=log
git commit -m "chore(applications): integrate Studio project workflow and learning updates"
git push --recurse-submodules=check origin main
git status
git submodule foreach --recursive 'git status --short --branch'

Linux

cd "$HOME/umicom/Umicom-Applications"
git status
git switch main
./build/linux-all-gtk4-debug/bin/umicom repo lock .
git add -A
git diff --cached --check
git diff --cached --submodule=log
git commit -m "chore(applications): integrate Studio project workflow and learning updates"
git push --recurse-submodules=check origin main
git status
git submodule foreach --recursive 'git status --short --branch'

For a headless-only Linux checkpoint, use the native tool from build/linux-gcc-all-headless-debug/bin/umicom instead. That records source revisions; it does not qualify a GTK release.

The recurse check verifies availability of referenced submodule commits on a remote, not that every checkout is attached to main. Check that intended changes are committed and pushed in each child, and that the parent's staged gitlinks identify those commits. A clean build-only detached submodule can legitimately remain at its recorded revision.

16. Continue on another machine

For a new machine, clone the parent and its recorded submodules. Authenticate with your normal GitHub setup when required.

Windows

Set-Location "C:\umicom"
git clone --recurse-submodules https://github.com/umicom-foundation/umicom-applications.git Umicom-Applications
Set-Location "C:\umicom\Umicom-Applications"
git status
git submodule status --recursive

Linux

mkdir -p "$HOME/umicom"
cd "$HOME/umicom"
git clone --recurse-submodules https://github.com/umicom-foundation/umicom-applications.git Umicom-Applications
cd "$HOME/umicom/Umicom-Applications"
git status
git submodule status --recursive

For an existing checkout, first save and publish or otherwise preserve local changes in every repository. From the clean parent root:

git status
git switch main
git pull --ff-only origin main
git submodule sync --recursive
git submodule update --init --recursive
git status

Do not add --remote to the submodule update when reproducing the parent's snapshot. Ordinary update checks out the recorded child commits; it does not choose whichever branch tip happens to be newest. A developer can attach a child to main after the branch comparison in section 1.

17. What to verify before calling Studio ready

A service test and a visible button answer different questions. Use the following checks on Windows and Linux GTK before promoting this build.

Area Acceptance check
New Project Opens a form, rejects an existing folder, creates source and adopts the right workspace.
Documents New, Open, Save, Save As, Save All, Undo and dirty-close protection operate on real editor text.
Multiple tabs A build saves every named draft; an unnamed draft blocks the build; the active tab is preserved.
Build configuration Changing folders changes source identity; imported Run is blank; a stale settings dialog cannot trust another workspace.
Background execution Configure/build/test/run/install do not block GTK; cancellation completes before another operation.
Diagnostics Intentional compiler error is visible; Run does not launch an old executable; recovery build succeeds.
Menus and search Main menu, toolbar and canonical Search Everywhere build commands follow the same route.
Installation Installed Studio opens outside the checkout, finds resources and completes the project exercise.
Lessons All 64 catalogue records are available; Notes model examples run; GTK Notes opens, saves and protects drafts.

Persistent project profiles, automatic imported-project target discovery, continuous output streaming, interactive run input, comprehensive debugger/LSP qualification, richer graphical lesson navigation and clean-machine installers remain follow-on work. Existing implementations are preserved, but they are not made complete merely by adding a menu entry.

The source audit and validation report in this delivery explain the evidence for each repair and the untested native parts. No remote commits or pushes were made while preparing the update.
