Building, testing and publishing Umicom Studio

Create a Windows deployment archive7. Build and test on Linux8. Install and package on Linux9. Publish the changed repositories10. Record child revisions in the parent11. This guide takes a developer from a local source checkout to a tested development installation and published Git commits. It uses the complete Umicom Applications workspace, where Framework and the application modules are separate Git repositories called submodules.

Follow one stage at a time. Configuring prepares the build instructions. Building creates executables and libraries. Testing checks their behaviour. Installing copies the files selected by the project's installation rules to a separate directory. Publishing with Git records source changes remotely; it does not replace any of those checks.

1. Check your starting point

The Windows examples use C:\umicom\Umicom-Applications. The Linux examples use $HOME/umicom/Umicom-Applications. Replace these paths if your checkout is elsewhere.

Before changing source, read the status in the parent and its children:

Set-Location "C:\umicom\Umicom-Applications"
git status
git submodule foreach --recursive 'git status --short --branch'

cd "$HOME/umicom/Umicom-Applications"
git status
git submodule foreach --recursive 'git status --short --branch'

Keep existing work safe. Do not overwrite unrelated local edits with a source update. A changed-file ZIP is an overlay: compare its umicom-applications folder with the existing checkout, merge the intended files, and keep files that are absent from the ZIP. Do not mirror-delete the checkout.

Check before switching branches

The normal development branch is main. Run git status inside a repository first. When it already reports On branch main, git switch main is harmless but not a substitute for that check.

A clean submodule may report HEAD detached at ... after cloning or updating. This means it is checked out at a particular commit, not attached to a branch. In that repository, compare:

git rev-parse HEAD main

The first line is the checked-out commit; the second is local main. If they match and the working tree is clean, switching to main changes the branch attachment without changing the source. If they differ, or there are uncommitted changes on a detached checkout, stop and review the work before switching. Do not force a checkout or assume git push origin main publishes the detached commit.

If local main does not exist, inspect git branch -a and ask a maintainer to help establish the intended tracking branch. Do not guess which branch contains the work.

2. Configure and build on Windows

Open PowerShell and run these commands one at a time:

Set-Location "C:\umicom\Umicom-Applications"
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"

Configure all enabled application modules, including the native tool and learning examples:

& "C:\msys64\ucrt64\bin\cmake.exe" --preset windows-ucrt64-all-debug -DBUILD_TESTING=ON -DUMICOM_BUILD_NATIVE_TOOL=ON -DUMICOM_BUILD_LEARNING_EXAMPLES=ON -DUMICOM_LEARNING_BUILD_GUI=ON

Read the final configuration result. If it reports a missing dependency or another error, fix that before building. Build with two parallel jobs:

& "C:\msys64\ucrt64\bin\cmake.exe" --build --preset windows-ucrt64-all-debug --parallel 2 -- -k 0

The -k 0 part tells Ninja to continue other possible work after an error, which can expose more than one problem in the same run. It does not turn a failed build into a successful one.

After a native command, $LASTEXITCODE displays its exit code. Zero normally means success. A nonzero result means you should read the error and stop before installation or publication.

3. Run the editor checks and the full Windows suite

CTest is CMake's test runner. These focused groups cover the document workflow, search navigation and the real headless Studio editor composition:

& "C:\msys64\ucrt64\bin\ctest.exe" --preset windows-ucrt64-all-debug --parallel 1 --no-tests=error --output-on-failure -R '^framework\.document\.editor_workflow\.'

& "C:\msys64\ucrt64\bin\ctest.exe" --preset windows-ucrt64-all-debug --parallel 1 --no-tests=error --output-on-failure -R '^framework\.editor\.search_navigation\.'

& "C:\msys64\ucrt64\bin\ctest.exe" --preset windows-ucrt64-all-debug --parallel 1 --no-tests=error --output-on-failure -R '^studio\.(editor_workflow|project_workflow)$'

Then run every registered test:

& "C:\msys64\ucrt64\bin\ctest.exe" --preset windows-ucrt64-all-debug --parallel 2 --no-tests=error --output-on-failure

--no-tests=error prevents a completely empty test selection from looking successful. Review failed, skipped, disabled and Not Run entries. A missing test executable needs a build correction; it is not a passed test.

4. Check the actual Windows application

From the same PowerShell window:

& ".\build\windows-ucrt64-all-debug\bin\umicom-studio-ide.exe"

Use a disposable Notes project and the guide at applications/studio/docs/EDITING_FILES.html. Check that you can open a file, change it, move between tabs, find next and previous occurrences, replace text, undo the replacement, save, build and run.

Also check the cases where Studio must protect your work. Close an unsaved document and choose Cancel. Repeat and deliberately discard it. Reopen the same file and confirm that it selects the existing tab. Start a build, request application close and check the running-work warning. Try a long replacement that exceeds the simple editor's text capacity and confirm that no partial replacement appears.

Close the window while a text or confirmation dialog is open, then reopen Studio. A dismissed dialog must not access an earlier runtime or discard another document. These are native interaction checks: passing headless service tests alone does not establish that the graphical callbacks behave correctly on your machine.

Use practice files and simulation data only. Do not use live orders, real payments or production workspaces as application smoke tests.

5. Install into a separate Windows directory

Close the applications. Choose a new installation directory:

Set-Location "C:\umicom\Umicom-Applications"
$Stage = "C:\umicom\installed\studio-editor"
Test-Path -LiteralPath $Stage

If the last command prints True, choose a different empty path and set $Stage again. Preserve the earlier installation. Then install:

& "C:\msys64\ucrt64\bin\cmake.exe" --install ".\build\windows-ucrt64-all-debug" --config Debug --prefix $Stage

Check an installed native command:

& "$Stage\bin\umicom-source-contracts.exe" --help

Now start the installed Studio, not the build-tree executable. Starting outside the source directory helps reveal missing installed resources:

$env:Path = "$Stage\bin;C:\msys64\ucrt64\bin;$env:Path"
Set-Location $env:TEMP
& "$Stage\bin\umicom-studio-ide.exe"

Repeat the editing exercise and check the learning pages. The public editing guide is installed at share\umicom\studio\docs\EDITING_FILES.html. The Framework document guide and SDK example are under share\umicom-framework.

This development installation uses your existing MSYS2 runtime. Installation success does not prove that every DLL, theme, schema or other runtime resource is bundled for an end user's machine.

6. Create a Windows deployment archive

Close Studio again. Use new package and deployment directories; do not unpack over a working installation:

Set-Location "C:\umicom\Umicom-Applications"
$PackageDir = "C:\umicom\packages\studio-editor"
$Deploy = "C:\umicom\deployments\studio-editor"
Test-Path -LiteralPath $PackageDir
Test-Path -LiteralPath $Deploy

Both paths should be absent. Then create one archive with a known filename and no extra enclosing directory:

& "C:\msys64\ucrt64\bin\cpack.exe" --config ".\build\windows-ucrt64-all-debug\CPackConfig.cmake" -G ZIP -C Debug -D CPACK_ARCHIVE_COMPONENT_INSTALL=OFF -D CPACK_INCLUDE_TOPLEVEL_DIRECTORY=OFF -D CPACK_PACKAGE_FILE_NAME=umicom-applications -B $PackageDir

Check the file, record its checksum, and extract it:

Get-FileHash -LiteralPath "$PackageDir\umicom-applications.zip" -Algorithm SHA256
Expand-Archive -LiteralPath "$PackageDir\umicom-applications.zip" -DestinationPath $Deploy
$env:Path = "$Deploy\bin;C:\msys64\ucrt64\bin;$env:Path"
Set-Location $env:TEMP
& "$Deploy\bin\umicom-studio-ide.exe"

Test the extracted copy before sharing the package. Repeat the required checks for the other products included in a suite archive. A package that runs only because your development machine supplies missing dependencies must not be described as self-contained. Verify it on a clean target machine before end-user distribution.

7. Build and test on Linux

For the graphical suite, use the repository's Linux GTK preset. Its dependencies, including the required GTK development libraries, must be installed:

cd "$HOME/umicom/Umicom-Applications"
cmake --preset linux-all-gtk4-debug -DBUILD_TESTING=ON -DUMICOM_BUILD_NATIVE_TOOL=ON -DUMICOM_BUILD_LEARNING_EXAMPLES=ON -DUMICOM_LEARNING_BUILD_GUI=ON
cmake --build --preset linux-all-gtk4-debug --parallel 2
ctest --preset linux-all-gtk4-debug --parallel 1 --no-tests=error --output-on-failure -R '^framework\.document\.editor_workflow\.'
ctest --preset linux-all-gtk4-debug --parallel 1 --no-tests=error --output-on-failure -R '^framework\.editor\.search_navigation\.'
ctest --preset linux-all-gtk4-debug --parallel 1 --no-tests=error --output-on-failure -R '^studio\.(editor_workflow|project_workflow)$'
ctest --preset linux-all-gtk4-debug --parallel 2 --no-tests=error --output-on-failure
./build/linux-all-gtk4-debug/bin/umicom-studio-ide

Run each line separately. In a Linux shell, echo $? immediately after a command displays its exit status. Stop on an error; do not proceed to installation after a failed build or required test.

For a machine without a graphical development environment, use the headless preset instead:

cmake --preset linux-gcc-all-headless-debug -DBUILD_TESTING=ON -DUMICOM_BUILD_NATIVE_TOOL=ON -DUMICOM_BUILD_LEARNING_EXAMPLES=ON
cmake --build --preset linux-gcc-all-headless-debug --parallel 2
ctest --preset linux-gcc-all-headless-debug --parallel 2 --no-tests=error --output-on-failure

The headless suite exercises services without a GTK window. It does not produce evidence of native graphical behaviour. Do not try to launch a GTK executable from a build that explicitly disables it.

8. Install and package on Linux

After successful graphical checks, choose a new path and install:

cd "$HOME/umicom/Umicom-Applications"
STAGE="$HOME/umicom/installed/studio-editor"
test ! -e "$STAGE"

The last command should succeed. If it fails, choose a new path rather than deleting the old installation.

cmake --install build/linux-all-gtk4-debug --config Debug --prefix "$STAGE"
"$STAGE/bin/umicom-source-contracts" --help
cd /tmp
"$STAGE/bin/umicom-studio-ide"

For a headless SDK installation, use build/linux-gcc-all-headless-debug in the install command and skip the GTK launch. The SDK example can still be built against that installation.

A Linux archive can be created and extracted into another new directory:

cd "$HOME/umicom/Umicom-Applications"
PACKAGES="$HOME/umicom/packages/studio-editor"
DEPLOY="$HOME/umicom/deployments/studio-editor"
test ! -e "$PACKAGES"
test ! -e "$DEPLOY"

Proceed only when both paths are absent:

cpack --config build/linux-all-gtk4-debug/CPackConfig.cmake -G TGZ -C Debug -D CPACK_ARCHIVE_COMPONENT_INSTALL=OFF -D CPACK_INCLUDE_TOPLEVEL_DIRECTORY=OFF -D CPACK_PACKAGE_FILE_NAME=umicom-applications -B "$PACKAGES"
sha256sum "$PACKAGES/umicom-applications.tar.gz"
mkdir -p "$DEPLOY"
tar -xzf "$PACKAGES/umicom-applications.tar.gz" -C "$DEPLOY"
cd /tmp
"$DEPLOY/bin/umicom-studio-ide"

As on Windows, test the extracted package with the intended runtime dependencies. Packaging is not a substitute for application checks.

9. Publish the changed repositories

Review source changes and successful tests before publishing. A commit message should describe the change; it does not certify a test run by itself. Keep credentials, local databases, generated binaries and unrelated work out of the commit.

For an editor change shared between Framework and Studio, publish Framework first, Studio second, then the parent. Other application submodules need a new commit only when their own source has changed. The appendix provides commands for every registered child repository.

After the branch checks in section 1, the usual Framework sequence is:

Set-Location "C:\umicom\Umicom-Applications\framework"
git status
git switch main
git status
git add -A
git diff --cached --check
git commit -m "feat(framework): improve editor navigation and working-copy safety"
git push origin main

For Studio:

Set-Location "C:\umicom\Umicom-Applications\applications\studio"
git status
git switch main
git status
git add -A
git diff --cached --check
git commit -m "feat(studio): connect editor search and document-safe confirmations"
git push origin main

Use the Linux directory commands from the appendix with the same Git operations. Run one command at a time. Nothing to commit, working tree clean means no new commit is needed in that repository; continue to its push. Everything up-to-date is a normal push result when local main is already published. Stop on other errors, including a rejected push. Do not force-push to make an error disappear.

10. Record child revisions in the parent

After the changed child pushes succeed, update the native repository lock. On Windows:

Set-Location "C:\umicom\Umicom-Applications"
git status
git switch main
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
& ".\build\windows-ucrt64-all-debug\bin\umicom.exe" repo lock .

On Linux after a graphical build:

cd "$HOME/umicom/Umicom-Applications"
git status
git switch main
./build/linux-all-gtk4-debug/bin/umicom repo lock .

A headless Linux build supplies the tool at ./build/linux-gcc-all-headless-debug/bin/umicom instead. Use the tool you actually built. If the lock command fails or the executable is missing, stop before committing the parent.

After a successful lock, the remaining commands are the same on both systems:

git add -A
git diff --cached --check
git diff --cached --submodule=log
git commit -m "chore(applications): update editor documentation and child revisions"
git push --recurse-submodules=check origin main
git status
git submodule foreach --recursive 'git status --short --branch'

The parent records commits from child repositories, not the files staged inside them. --recurse-submodules=check checks that changed child commits are available on at least one child remote-tracking branch before allowing the parent push. It does not stage or commit a dirty child for you.

11. Continue on another machine

Publish the changed children and parent before moving to another machine. To create a new checkout on Windows:

New-Item -ItemType Directory -Force "C:\umicom"
Set-Location "C:\umicom"
git clone --recurse-submodules https://github.com/umicom-foundation/umicom-applications.git Umicom-Applications

On Linux:

mkdir -p "$HOME/umicom"
cd "$HOME/umicom"
git clone --recurse-submodules https://github.com/umicom-foundation/umicom-applications.git Umicom-Applications

The destination must be new. To update an existing clean checkout, enter its parent directory and check both parent and child status before these commands:

git status
git submodule foreach --recursive 'git status --short --branch'
git switch main
git pull --ff-only origin main
git submodule update --init --recursive

Do not proceed over unfinished work. The submodule update uses the commits recorded by the parent, which can leave child repositories detached. That is normal for reproducing or building a published snapshot. Review branch attachment before developing in a child; do not replace the recorded snapshot with every remote branch tip automatically.
